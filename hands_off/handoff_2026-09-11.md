## 2. Data-format facts — established by checking, do not re-derive

### 2.1 `bk<N>` in ANSYS filenames is a ROW POSITION, not a tree number

`bk3` → `B21_S07`, `bk8` → `B21_S12`. The mapping comes from the description
file: column 0 = row order, column 2 = tree number.

**Proof that settles it:** tree number 3 does not exist in the dataset (trees
are 1, 4, 7, 8, 9, 10, 11, 12, 13, 14, 16, 21, 24), yet `out_static_bk3_*`
exists. Independently confirmed by Bara: `bk3` and `bk8` are trees 7 and 12.

This was silently wrong before. `bk8` would have been read as tree 8 — which
*does* exist — pairing one tree's model with another tree's measurements, with
no error and a correct-looking plot. `bk3` failed to match anything, which is
the only reason it surfaced.

### 2.2 Tree IDs

Canonical form everywhere: `B21_S{nn}`. The experimental dataset uses
`BK{nn}` for the same tree; `bk_id_to_canonical()` converts. Without it no
experimental row ever matches a FEM row **and nothing errors** — the plots
just come out empty.

### 2.3 `Popis_Babice_VSE_09012025_ans_lev6_0_azimcor.txt`

Read by position, verified: 0 = row order, 2 = tree number, 7 = anchorage
height, 9 = level III, 12 = level VI (0 for most trees). All 13 trees pass the
ordering check `anchorage > level3 >= level6`. Lives in `scripts/ansys/`, the
same folder ANSYS reads, deliberately.

### 2.4 `geom_*.txt` — same layout for AdTree and TreeQSM exports

```
line 1        "0 1 2 ... 10", column-index row. ANSYS does not count it.
column 0      row index, 1..n
columns 1,2,3 x, y, z of the cylinder START point
column 4      LENGTH (m)
column 5      RADIUS (m)
columns 6,7,8 unit direction vector
column 9      parent index
column 10     branch order, 0 = trunk
```

Cylinder volume = `pi * r^2 * L`.

**Verification if this is ever in doubt:** on
`geom_B21_S12_man_pd04-002-05_mo9_sr010_ri1_1` the total comes to 3.042 m³
against 3.065 in `volume_results.csv`, and trunk diameter at 1.0–1.6 m to
0.288 m against a field DBH of 0.30. Swapping columns 4 and 5 gives 19.5 m³
and a 1.77 m trunk.

**`n_rad` = last index in column 0 = lines − 1.** Confirmed on all 12 exports.
This is the number that goes on line 26 of `bk_kp.mac`.

### 2.5 Modal output

Parsed **by position against a hardcoded 19-name list**, because the file's own
header repeats shorthand names across the PFACT and EFF MASS groups. Anything
past the list is dropped with no error.

`TIME_kg` and `TIME_incl_rots` are the **6th and 5th columns from the END** —
indexed from the end on purpose, so a column added elsewhere cannot shift them.

`M_total` is on the first line: `TOTAL MASS of MODEL =`. Found by searching the
first few lines, not by a fixed index.

## 3. The finding that matters most

### `M_total` is 96–97 % root plate

The mass in the modal output is the whole model, and the root plate dominates
it. Root plate: diameter `20 × DBH`, thickness `2.18 × DBH + 0.13`, soil
density `densp = 1200`. Wood is `densw = 1184`.

```
B21_S04   plate 74 404 kg + tree 2 340 kg = 76 743   reported 76 716   (+0.04 %)
B21_S12   plate 26 600 kg + tree 1 060 kg = 27 660   reported 27 650   (+0.04 %)
```

The tree is **3.0 % and 3.8 %** of model mass respectively. `MTOT` is correct;
it simply is not the mass of the tree.

**Consequence: `f_total` in `modal_effmass.csv` is invalid.** It divides by the
root plate. The figures reported "captured 0.19 %" and "captured 18.25 %";
those numbers cannot be read as the fraction of tree mass captured.

Recomputed against tree mass (cylinder volume × 1184), B21_S12:
- `adtree_r5mm`: ~53 kg captured against 1 060 kg tree → about 5 %
- `treeqsm_pd002`: ~5 510 kg against ~3 629 kg tree → **more than the whole
  tree**, so the root plate is moving in those modes

**Action for next session:** normalize by tree mass, not model mass. Either
from geometry (`pi r^2 L` summed × 1184) or in APDL via
`esel,s,mat,,1` / `esel,s,mat,,2` with `*GET,...,ELEM,0,MTOT,x`.

`f_captured` is unaffected — it divides by the sum over modes.

| B21_S12 | 171.3 | 174.0 | 142.9–177.0 | −1.5 % |

| tree | FEM | measured (Pt3/Pt4) | diff |
|---|---|---|---|
| B21_S07 | 2.049 | 2.30 / 2.35 | −12 % |
| B21_S12 | 0.489 | 0.88 / 0.91 | −45 % |

### 4.2 Rotation stiffness is CALIBRATION, not validation

Root-ball height was tuned iteratively on these beeches to match the static
pulling test — deliberately, so that dynamics could then be assessed. Its
agreement therefore measures the tuning, not the model.

**Write it that way: statics is calibration, dynamics is validation. Never both
by the same quantity.** Root-plate radius and the other parameters come from
literature and earlier sensitivity analyses — the text must distinguish which
parameter was tuned on this data and which was adopted.

Displacement stiffness was *not* tuned (root-ball height drives base rotation;
the −12 % / −45 % arises in trunk bending above it), so it stands as
independent. So does frequency.

### 4.3 Rotation stiffness cannot discriminate between models

Force is an input, lever arm is geometry, and the root ball is a controlled
constant per tree. Same moment ÷ same rotation = same stiffness. r10 and r20
produced identical values. **This is a result to state, not a bug to fix.**

`DISPLx_MAX_mm` is also not comparable across models — it is a maximum over a
*different node set* (a higher radius threshold prunes branch tips), so it
measures model extent, not stiffness. `DISPLx_level3_mm` has a defined common
read-out point and is the usable one.

### 4.4 Measurement uncertainty is comparable to model error

cam vs nocam on rotation stiffness: B21_S07 +1.7 % vs +25.6 %, B21_S12 −1.5 %
vs −23.4 %. **The choice of sensor changes the conclusion more than the choice
of model.** Figure A shows this as a grey band around zero; a model point
inside the band is not distinguishable from the measurement.

## 5. Open items

1. **Number of extracted modes.** 20 is too few — the bending mode is not
   reliably among them. Suggested: run 200 modes on B21_S16 (4 072 cylinders,
   cheap) and see where cumulative captured mass jumps. A `MODOPT` window with
   non-zero `FREQB` around 0.15 Hz would be cheaper, but only after the
   diagnostic run shows where the bending pair sits. Harmonic peaks (~0.22 Hz)
   suggest where to look.
2. **`treeqsm_pd002` parameter fault.** Three trees have a *negative*
   `slope_displacement`: B21_S08 (−21.07), B21_S09 (−13.65), B21_S14 (−0.47),
   giving deviations to −2240 %. Cause known to Bara, being worked separately.
   `DEVIATION_EXCLUDE_MODELS = ["treeqsm_pd002"]` produces the trimmed figures.
3. **`phi` direction.** The handoff defines
   `phi = V_branch,AdTree / V_branch,TreeQSM`, but the quoted range 1.5–17.7
   only matches the inverse. `method_deviation_overview.py` used the inverse
   and printed the discrepancy. **Resolve this before the density-scaling
   experiment** — scaling the wrong way would be invisible.
4. **Model name spelling.** `adtree_r5mm_no acel` (space) and
   `treeqsm_pd002_no_acel` (underscore) both occur in the CSVs. Matching is
   tolerant, display is not normalized on purpose — **fix at the ANSYS source**
   or it returns.
5. **Regressions C and D are not yet readable.** R² = 0.011 and 0.017 at n = 16,
   but the y-axis is frequency deviation, which the mass issue contaminates.
   Rerun after §3 is fixed. `phi` on a log x axis; keep n in the title.
6. **`MODEL_INCLUDE` / `MODEL_INCLUDE_SUFFIX` can disagree**, producing a file
   whose name claims a filter that is not active. A guard was suggested, not
   yet added. In `method_deviation_overview.py`, `model_colors` is computed
   from the *narrowed* list, so a model's colour can differ between filtered
   and unfiltered runs — fix to use all models in the data.
7. **`trunk_m3 + branch_m3` vs `total_m3`** consistency check was requested in
   the volume-summary extension; result not yet seen.
8. **Two `002`-variant files** (B21_S08, B21_S09) reported no trunk cylinders
   between 1.0 and 1.6 m. The test looks at the cylinder **start point** only,
   so a long cylinder spanning 1.3 m is missed. Fix the test to find the
   cylinder *crossing* 1.3 m. Geometry is fine — visually confirmed.
9. **`bk_kp.mac`, line ~110: `else` should be `*else`.** Unverified. If it is
   plain `else`, the trunk gets `MAT=2` and branches keep whatever attributes
   they had — invisible in the mesh, wrong in the material assignment. Check
   by counting lines per material after `allsel`.
10. **APDL parameter names exceed the 32-character limit.**
    `t_tme_rots_sq_bk8_scenario1_mode1` is 33 characters at the shortest
    possible combination. If ANSYS truncates rather than errors, different
    modes collapse onto one parameter. Quick empirical check: does column 15 of
    an existing `out_modal_*.txt` vary between modes, or is it constant?
11. **TTEM is a norm over x/y/z and three rotations.** Fine for ranking. It
    cannot be normalized by model mass, because a norm does not sum to the
    total. If a mass fraction is wanted, use the **sum** of the three
    translational effective masses, and keep translations and rotations
    separate.

## 7. Method notes worth keeping

- `*GET` item for mass is **`MTOT`**, not `MASS`.
- ANSYS writes into `scripts/ansys/` while running. Loading results mid-run
  gives an incomplete picture, and a half-written file will be skipped by the
  ten-value check rather than silently mis-parsed. Re-run the pipeline after
  the solve finishes.
- `trunk_taper_error_summary.csv` is the **error of the median model**, not the
  median of the errors. The two differ by up to 0.5 pp. Label the column.
- Nominal wood density `densw = 1184` kg/m³, read from `bk_kp.mac`.
